## 〇、一句话现状（2026-10-02 更新，**以此为准**；最新一轮结论在 **§十五**）

树是 **OH 6.1（6.1.0.31 / API 23）**，lubancat4 已多次构建成功并刷机运行。
**2026-09-30 夜 ~ 10-01 的连续攻关把"显示链路全黑"打到了收尾**：

- ✅ **鼠标抖动/闪烁/丢帧已修复**（composer 每帧 modeset + EBUSY，见 §10.2，用户实测确认不闪）；
- ✅ **开机黑屏已修复**（板级自愈脚本，重启后自动撤掉 `BootAnimationNode` 黑层，见 §10.3）；
- ✅ **`deviceLocked` 已修复**（`AuthStateInit` 不再默认置锁，见 §10.2）；
- ✅ **解锁后桌面窗口与背景已经能显示**（不再黑屏）——根因是 launcher 把"建桌面窗"放在会挂死的
  `await getRdbStore()` 之后，已把建窗提前并给卡死的 await 加限时兜底（见 §11.5 / §11.6）；
- ⚠️（**历史口径，已被下面的 2026-10-02 更新取代**）**仍未完成：桌面图标**。当时的判断是总根因 —— `user 100` 从未真正解锁
  （`IsOsAccountUnlocked: account verified status: 0`、`LnnGenerateCeKeyByHuks: user not unlocked`）
  → **凭据加密区（CE / el2）整体不可用** → launcher 的 S3 RDB 挂起、el2 数据目录/清单文件不存在
  → 桌面清单为空（见 §11.7）。

**已更新（2026-10-02）**：
- ✅ **`user 100` 解锁这条链已在 §13 打通**（根因是 `/data` 上 el1 目录被明文填满 → fscrypt 策略设不上；
  清空 `/data` 后 fscrypt/el2/CE 全部自愈，账号不再返回 30）。
- 🔴 **但桌面图标仍为空，且找到了更直接的上游根因（新，见 §十五）**：
  **本板上所有 promise / callback 形态的 napi 异步 API 的完成回调都不会回到 JS** ——
  `uv_queue_work` 的 worker 正常执行，但 `AsyncAfterWorkCallback` 永不触发（进程内没人驱动 napi 的 uv loop，
  没有 `UVLoop` 线程、没有挂 `postTask_`）。这解释了 §11.5「`getRdbStore` 永不 settle」、
  §11.7「清单两条来源都拿不到」、§14.4「napi 原生 done 但 JS 不继续」的**全部现象**。
- 它是**系统侧 ACE/napi 的集成缺陷**，与 launcher 工程、与"自编/预编译组件差异"都无关
  （已用独立探针 App 逐条证伪，见 §15.3）。

**下一步的最高优先级 = §十八 的 18.4/18.5**：**根因已彻底查明为 libuv 编译宏三方不匹配**
（`USE_OHOS_DFX` 开 + `USE_FFRT` 关 → after-work 的两条派发路径一条被 `return`、一条被 `#ifdef` 编掉）。
**修法只需改一行**（`libuv_use_ffrt = true`，或关掉 `use_ohos_dfx`）→ 重编 `libuv.so`（分钟级）→ 推库重启 → 跑探针验收。
打通后不仅图标，相册/联系人等所有依赖异步 napi 的应用都会一并恢复，
§11 / §14 里给 launcher 打的 bring-up 补丁也都能逐条回退。

### 10.5 当前唯一阻塞：ability 建窗失败（桌面出不来）

- 现象：`Launcher_Default: WindowManager --> findWindow errCode:1300002, msg: The window is not created or destroyed`；

### 11.2 ★ 本轮修复：launcher 的 RDB 安全级别 S3 → S1（关键）

- **根因**：`applications/standard/launcher/common/.../RdbStoreManager.ts` 的 `initRdbConfig()` 用
  `securityLevel: relationalStore.SecurityLevel.S3` → **S3 = 凭据加密区（EL3/CE）**，而本板
  `strongauthmanager: IsOsAccountUnlocked: account verified status: 0`（user 100 **从未真正解锁**，
  只有屏幕锁状态被我们改过）→ CE 不可用 → `getRdbStore(S3)` 的 Promise **永不 settle**
  → `await initRdbConfig()` 卡死 → 后面的 `createWindow('EntryView')` 永不执行 → 无桌面。
- **修复**：改为 `SecurityLevel.S1`（设备加密区 EL1，开机即可用），注释含回退说明。
- **证据（修复后）**：RDB 服务侧 `IsConfigInvalidChanged: Illegal change, storePath:/***/el1/***/Lau***.db,
  securityLevel: 3 -> 1`，随后 `ConnectionPool: Create ... app[com.ohos.launcher:phone_launcher] area[el1] ...Lau***.db`
  → 建库成功；launcher 的初始化**明显前进**（已跑到 `createRecentWindow()` 那一带：
  `WindowManager --> hideWindow/findWindow, name RecentView`）。
- **部署方式**：重编 HAP（`hvigorw`，~8 秒）→ 推 `/system/app/com.ohos.launcher/Launcher.hap` →
  **`bm install -r -p <hap>`**（比手删 BMS 缓存干净）→ 重启。

## 十三、2026-10-01 下午：**user 100 解锁的总根因已找到并修复**（本节结论经板上实测，权威）

### 13.1 一句话结论

**总根因不是 os_account / useriam / huks 的逻辑，而是 `/data` 上的 el1 目录在"没有加密策略"的状态下被历史启动写满了明文文件，导致 fscrypt 策略永远设不上 → 储守护进程的密钥准备流程中断 → 每用户 el2/el3/el4/el5 密钥目录从未创建 → EL2 激活失败 → `user 100` 永不 `verified` → CE/el2 整体不可用。**
**处置：清空 `/data`（= 干净首启）后，上述链条全部自愈。**

### 13.2 证据链（全部板上实测）

**① 账号侧**：`SendToStorageAccountStart` 调存储 `UnlockUser` 失败 → `isUserUnlocked=false` → 永不 `SetOsAccountIsVerified(100,true)`

## 十五、2026-10-01 夜 ~ 10-02 凌晨：★ 应用级 napi 异步总缺陷（uv loop 无驱动）

> 本节是**新发现的上游根因**，解释 §11.5 / §11.7 / §14.4 里所有"napi 原生说 done、JS 却不继续"的现象。
> 全部结论均有板上实测证据；脚本与产物索引见 15.8。

### 15.1 一句话结论

**本板上"所有 promise / callback 形态的 napi 异步 API 的完成回调都不会回到 JS"**（RDB、preferences、
bundle 查询、账号、dataShare …）：`uv_queue_work` 的 worker 正常执行，
但 **`AsyncAfterWorkCallback` 永不触发** —— 因为**应用进程里没有任何"驱动 napi uv loop"的人**
（没有 `UVLoop` 线程，也没有挂 `postTask_`）。

- 这**不是** launcher 的问题，也**不是**"自编 HAP 与预编译组件不匹配"，而是**系统侧 ACE/napi 的集成缺陷**（本端口特有）；
- launcher 的 `getRdbStore` 挂起（§11.5）、清单查询不回 JS（§14.4）、`GridLayoutInfo.json` 不生成（§11.7）、
  原厂 launcher HAP 不建窗（§10.4）**都是它的下游表现**。

### 15.2 证据链（全部板上实测、可复现）

**① 四形态探针（探针 App，见 15.3）**

```
SUMMARY  microtask=true timer=true syncNapi=true
         napiPromise=false napiCallback=false preferencesPromise=false rdbPromise=false   ❌
```

**② 原生侧 Debug 日志（`hilog -b D`）**

```

D C03f01/NAPI: [(native_async_work.cpp:223)(AsyncWorkCallback)] ...AsyncWorkCallback start to execute.  ← worker 跑了
```

### 16.1 目的与方法（只观测、不改行为）

在 napi 侧加**只读**埋点，回答三件事：① 有没有人给应用的 engine 挂 `postTask`/`CheckUVLoop`；② JS 线程到底有没有在泵 uv loop；③ worker 的结果有没有回到 JS 线程。

- 埋点文件（全在 `foundation/arkui/napi`，产物 `libace_napi.z.so`）：
  - `native_engine.cpp`：`SetPostTask()`、`CheckUVLoop()`、`UVThreadRunner` 启动、`Loop()`、`PostLoopTask()`、`CancelCheckUVLoop()`（每条只打前 5 次，避免刷屏）；

  - 统一前缀 `[E0-NAPI]`。

### 16.3 结论（板上实测 + 源码级佐证）

1. **应用进程里根本没有 uv loop 驱动**：`SetPostTask` / `CheckUVLoop` / `UVThreadRunner` / `Loop` / `PostLoopTask` / `AsyncAfterWorkCallback` **一次都没执行**，也没有 `UVLoop` 线程（对照实验已排除"日志被过滤"）。
2. **链路断点精确到一跳**：`uv_queue_work` 投递成功、worker 正常执行，**只有"worker 完成 → 回 JS 线程"这一跳丢失** —— 因为 `uv_queue_work` 的 after-work 回调必须由**跑 `uv_run` 的线程**触发，而本进程没有任何人在跑。
3. **应用走的是 declarative（1.1）前端**：探针进程 maps 里有 `libace_compatible.z.so` + `libarkruntime.so`，**没有** `libarkts_frontend*.so`（即没走 1.2/ANI 的 `ArktsFrontend`）。
4. **代码级佐证：stage 应用的主窗口 UI content 是"带非空 runtime"创建的**，链路如下（全为本树源码）：
   - `foundation/window/window_manager/wm/src/window_impl.cpp:696` `WindowImpl::UIContentCreate(ability, env, isAni)`：`ability == nullptr`（stage 模型正是如此）→ `UIContent::Create(context_, reinterpret_cast<NativeEngine*>(env))`（**非空**）；
   - `adapter/ohos/entrance/ui_content_impl.cpp:2336`：`if (runtime_) { container->GetSettings().SetUsingSharedRuntime(true); container->SetSharedRuntime(runtime_); }`；
   - `adapter/ohos/entrance/ace_container.cpp:662`：`if (GetSettings().usingSharedRuntime) jsEngine = loader.CreateJsEngineUsingSharedRuntime(instanceId_, sharedRuntime_);`
     → `JsiDeclarativeEngine(instanceId, runtime)`（`.h:297` 构造即把 `runtime_` 置为非空）；
   - `frameworks/bridge/declarative_frontend/engine/jsi/jsi_declarative_engine.cpp:1628` `EngineTask(bool sharedRuntime)`：**只有 `if (!sharedRuntime)` 里才 `SetPostTask + CheckUVLoop`**。
   ⇒ 于是 `sharedRuntime != nullptr` → **ACE 主动跳过挂接**，与实测 ①完全吻合。
5. **全树没有第二个挂接点**：`grep -rn "CheckUVLoop|SetPostTask("`（排除 `arkui/napi`、test）只命中 ACE 的三处前端（`jsi_declarative_engine` / `jsi_engine`（FA）/ `jsi_pa_engine`（PA，用 `Loop(LOOP_ONCE)` 自泵））；`jsi_declarative_engine.h` 的 `RunNativeEngineLoop()` 只被 `adapter/preview`（IDE 预览器）调用；`napi_run_event_loop` 全树**只有定义没有调用者**。
   ⇒ **在本树里，"该由谁驱动"的答案是"没有人"**；上游把这件事定义成"由共享 runtime 的拥有者代管"（见 §15.4 与 master 版代码的注释），而我们的链路上那个"拥有者"没有代管。
6. 附带确认：`arkTSMode`（`app.arkTSMode`，取值 `dynamic/static/hybrid`，由 `bundlemgr/module_profile.cpp` 从 HAP 解析）在**我们的 HAP 与出厂 HAP 上都是 `dynamic`** ⇒ 走的是 `FrontendType::DECLARATIVE_JS`，不是 `STATIC_HYBRID_DYNAMIC` 分支；**问题点就是"共享 runtime + 无人驱动"**，与 1.2/ANI 无关。

### 16.4 本轮新增的构建/链接踩坑（接 §15.5，下次先读）

1. **不要为了绕 ccache 去改 `toolchain.ninja`**：sed 掉 `/usr/bin/ccache` 会改掉 3 条编译 rule 的命令行 ⇒ ninja 判定**全图 25339 个目标**全部过期（开始全量重编）。正确做法是保持 ninja 图原样、用 `CCACHE_DISABLE=1`（ccache 直通，不读缓存）。
2. **`touch` 产物不能消脏**：`-d explain` 显示真实原因是 `stored deps info out of date`（`.ninja_deps` 记录的 mtime 过期）与 `output ... doesn't exist`；`ninja -t restat` 反而把脏集合从 8937 抬到 14350。
3. **ACE 的 `libace_compatible.z.so` 是"半残"状态**：它的链接输入共 3636 个对象，**其中 16 个 `.o` 已被删除**（`popup_element.o`、`render_select.o` …），可单独补齐（`ninja -t commands <obj>` 取命令、去掉 ccache、`xargs -P 8` 并行编译，约 1 分钟）。
4. **ACE 链接会卡在版本脚本**：`-Wl,--version-script=../../foundation/arkui/ace_engine/build/libace.map` 是**源模板**（首行裸 `{`、用 `?` 当通配符、`~` 未加引号），直接喂给 `ld/lld` 会报 `unknown directive: {` / `syntax error in VERSION script` —— 说明上游构建链里还有一步"生成可用的 map"的动作，手工链接需要额外处理（或暂时去掉该 flag，仅用于诊断库）。
5. **napi 库是"静态库 + solink"结构**：只重编 `native_engine.o`/`native_async_work.o` 不够，**必须重跑归档**（`libace_napi_static.a` 或等价归档）后再链接，否则产物里看不到新代码（本轮第一次就踩了：产物 md5 变了但 `strings | grep E0-NAPI` 为 0）。

## 十八、2026-10-07 深夜：★★★ 根因**彻底查明**——libuv 编译宏三方不匹配（本节为最终结论）

> 承接 §17.7 第 1 条。本节把"为什么 after-work 永不回到 JS"追到了**编译期宏组合**这一层，
> 全部判据均为**板上/构建产物实测**（非推断）。**结论：这不是 ACE/napi/ability_runtime 的逻辑缺陷，
> 而是本 port 的 libuv 构建配置与 libuv 源码的 `#ifdef` 结构不匹配。**

### 18.1 一句话结论

**本板 libuv 编入了 `USE_OHOS_DFX` 但**没有**编入 `USE_FFRT`，而 libuv 源码里"after-work 派发"的
两条路径恰好被这两个宏**割裂**：能工作的那条（改道）在 `#ifdef USE_FFRT` 里、被编掉了；
剩下那条（传统 `wq_async`）又在 `#ifdef USE_OHOS_DFX` 下被 `return` 掉。于是 after-work 回调
在任何情况下都不会被调用。**

### 18.2 三方证据链（环环相扣，均可复核）

**① 实测宏定义（从 ninja 图直接读，最硬）** —— `out/rk3588/obj/third_party/libuv/libuv_source.ninja`：
```
-DUSE_OHOS_DFX  -DSUPPORT_INTERRUPT  -DENABLE_WORKER_PRIORITY  -DASYNC_STACKTRACE
（无 -DUSE_FFRT）                       ← ★ 关键
```
来源：`third_party/libuv/libuv.gni`
```
libuv_use_ffrt = false     ← 默认 false（决定 USE_FFRT 不定义）
use_ohos_dfx   = true      ← 默认 true （决定 USE_OHOS_DFX 定义）
```
（`third_party/libuv/BUILD.gn:180` `if (libuv_use_ffrt && is_ohos) → USE_FFRT`；
  `:197` `if (use_ohos_dfx && is_ohos && !is_emulator) → USE_OHOS_DFX + SUPPORT_INTERRUPT`）

**② 板上库的符号判据** —— `/system/lib64/platformsdk/libuv.so`（184432 字节）：

> 本节的**决定性判据是①**（直接读 ninja 图的 `-D` 宏）：`USE_FFRT` 在
> `out/rk3588/obj/third_party/libuv/*.ninja` 中出现 **0 次**，且无任何 `-D*FFRT*`。

**③ 源码里的三条路（互斥关系）** —— `third_party/libuv/src/threadpool.c`：
```c

#ifndef USE_FFRT
    ...
    uv__queue_insert_tail(&w->loop->wq, &w->wq);
    uv_async_send(&w->loop->wq_async);        // → 触发 uv__work_done

#ifdef USE_OHOS_DFX
    if (uv_check_data_valid(loop) == UV_REGISTER_MAINTHREAD_FLAG) {
        return;                                // ★★ after_work_cb 永不执行
    }
#endif
    ...

//    而 uv_check_data_valid() 在"注册过 post_task_func"时返回该 flag（本板确实注册了，见 §17.3）

#ifdef USE_FFRT
void uv__work_submit_to_eventloop(...) {

        ... .func = uv__task_done_wrapper ...
        data->post_task_func(&task_info);      // ★ 本该由这里接手

}
#endif
```

## 十九、2026-10-08 凌晨：L1/L2 修复的**编译耗时实测**（全部现场测量，可直接据此安排下一轮）

### 19.1 结论（一句话）

### 19.2 实测数据（逐项，均为现场计时）

| 步骤 | 实测 | 说明 |
|---|---|---|
| ① 单个源文件编译（无 ccache） | **0.04~0.05 秒** | `threadpool.c`；`unix/core.c` 0.10 秒 |
| ② **全部 38 个编译单元并行重编（16 核）** | **1 秒** | 手工 `xargs -P16` 去掉 ccache 实测；38/38 成功 |
| ③ **全量重编 libuv.so（删光 .o 后 ninja 实编）** | **12 秒** | 含 38 个 CC + SOLINK + STAMP，共 41 条边 |
| ④ 单文件改动后的增量重编（touch 一个 .c） | **39 秒** | 420 条边（含若干无关 STAMP/SOLINK 被顺带重建） |
| ⑤ **GN 重生成**（改 `libuv.gni` 后的必经步骤） | **20 秒** | `gn gen .` 实测 |
| ⑥ 推库 + 重启 + 验证 | ~1 分钟 | `hdc file send` ~1 秒；`sync; reboot` + 等待上线 ~35 秒 |
| **合计（L1 或 L2）** | **≈ 2~3 分钟** | ②③⑤⑥ 之和，且**只重建 libuv 一个模块** |

### 19.3 为什么传播面这么小（三条实测依据）

1. **这两个宏只定义在 libuv 自己的 `BUILD.gn`**（`:181` `USE_FFRT`、`:198` `USE_OHOS_DFX`），
   全树其它地方的 `*USE_FFRT*` 都属 samgr 单测的 `SAMGR_USE_FFRT`，**与本缺陷无关**
   ⇒ 改宏**只影响 libuv 自身**的 38 个 `.o` 与 1 个 `.so`。
2. **`libuv.so` 是 `solink` 共享库**（非静态库）：运行时动态加载，
   改它**不需要重链任何依赖方**（`ninja -t query` 确认其输出只有 `libuv.so` 与 unstripped 版本）。
3. **依赖它的是运行时 NEEDED 关系**（如 `libace_napi.z.so` 通过 `uv_*` 符号使用），
   推一个新 `libuv.so` 即可生效，**无需动 ACE / napi / ability_runtime**。

### 19.4 唯一需注意的两点

1. **改 `libuv.gni` 会触发 GN 重生成（20 秒）**：该文件在 `build.ninja.d` 的输入列表里
   （`build_configs/thirdparty/libuv/BUILD.gn` 与 `libuv.gni`），ninja 会自动重跑 `gn gen`。
   **需注意**：本 out 目录的 ninja 图曾出现 `multiple rules generate ...`（文档 §7.2/§16.4），
   如 GN 重跑后报该错，按老办法加 `-w dupbuild=warn`。
2. **选 L1 会新增 `ffrt:libffrt` 依赖**：`BUILD.gn:299` `if (libuv_use_ffrt) → external_deps += [ "ffrt:libffrt" ]`，
   当前链接行里**没有** libffrt；开 L1 后会新增该依赖（`libffrt` 在 out 里已构建，无需额外编译）。
   **若想要最小副作用，选 L2**（关 `use_ohos_dfx`，不引入新依赖）。

### 21.3.0 ★★ 最终根因（日志直接证明，逻辑完全闭合）

### 21.3.0.1 storage_daemon 为何 exit 127（继续下钻的结果）

**已排除的**：
- ❌ 二进制不存在：本地 `out/rk3588/packages/phone/system/bin/storage_daemon` **存在**（1,351,960 字节，ELF aarch64）；

- ❌ `execv` 失败：日志里**没有** `[startup_failed]failed to execv`
  （该日志由 `init_service.c:37-39` 在 `execv` 失败时打印）—— 说明 **exec 成功了**。

**关键新证据（真正的起点）**：
```

         '/data/service/el1/public/storage_daemon/radar' failed, err=2.
```
这一行来自 `storage_daemon.cfg` 的 `post-fs` job：
```json

          "mkdir /data/service/el1/public/storage_daemon/radar 0640 root root" ]
```
⇒ **`/data/service/el1/public/...` 这个路径不可用（err=2 = ENOENT）**，而这正是需要 fscrypt 策略的 el1 目录。

**⇒ 真正的故障是："`storage_daemon` 服务在 21 秒内没能就绪，而 init 把这个失败当成致命错误。"**

`13600014` = `STORAGE_SERVICE_SYS_CAP_TAG (13600000) + 14` = **`E_SERVICE_IS_NULLPTR`**
（定义见 `interfaces/innerkits/storage_manager/native/storage_service_errno.h`）。

**断电为什么会导致这个**（两条同时作用）：
1. `/data` 处于 `sudden-power-off` checkpoint → 启动时多了 fsck/重挂等耗时路径，**整体启动变慢**；
2. `storage_daemon` 依赖链（samgr → storage_daemon → 挂载 /data → fscrypt）在 21 秒窗口内没走完
   → `init` 的 `init_global_key` 命令超时失败 → `[startup_failed]` → **init 主动 panic 重启** → 死循环。

### 21.3.1 ★★ 这是一个**健壮性缺陷**（用户明确指出："启动时断电是很正常的"）

- **断电（非正常关机）是嵌入式设备的常态**，设备**必须**能从中恢复，而不是陷入 panic 死循环；
- 缺陷点有两处：
  1. **`init` 对"用户密钥初始化失败"的处置过重**：`DoInitGlobalKey` 失败即 `startup_failed`
     → `ExecReboot panic`，没有重试/降级路径（`base/startup/init/services/init/standard/init_cmds.c:916`）；

     断电后启动变慢时不够用。
- **与 napi/libuv 主线无关**，是一个**独立的、优先级很高的启动健壮性问题**。

**已被日志直接证明的**：
- ✅ `init_global_key` 失败 = `CheckServiceStatus` 超时（耗时 21523ms = 21 秒上限，日志刷到 950 次）；

- ✅ 用户确认断电是触发点；且调试侧对设备的**写操作成功次数为 0**（见 §21.2.1）。

### 22.2 ★★ 根因最终定论：**fscrypt 与 storage_daemon 的循环依赖死锁**

**关键证据（`/tmp/reboot_watch.log`）**：
```
[ 4.692] checkpoint state = 44 : crc compacted_summary sudden-power-off   ← 断电留下的
[ 5.434] sdc: fscrypt cmd: init_global_key
[ 5.45~] CheckServiceStatus: "check storage daemon status ... 950 times"   ← 轮询 21 秒
```

**完整因果链（最终版，方向已订正）**：
```
断电（非正常关机）
  → /data 留下 "sudden-power-off" checkpoint（F2FS 固有行为）
    → fscrypt init_global_key 失败（它要通过 IPC 调 storage_daemon，等 21 秒超时）
      → /data 的 el1 加密目录全部建不出来（75 处 err=126 ENOKEY）
        → storage_daemon 依赖这些目录 → 启动即失败 exit(127)
          → init 判 critical 服务 4 次崩溃 → ExecReboot("panic") → 每 ~48 秒循环
```

**⚠️ 这是"循环依赖"死锁**：
| 环节 | 依赖谁 |
|---|---|
| `fscrypt init_global_key`（`sdc`）| **需要** `storage_daemon` 提供 SA（`CheckServiceStatus` 等它）|
| `storage_daemon` 启动 | **需要** `/data/service/el1/...`（fscrypt 加密目录）|

正常启动时序能打破它，**断电后时序被打乱 → 永久死锁**。

### 23.3 ★ 关键教训：**推系统库的正确姿势**（连续 3 次失误换来的）

**错误做法**（我犯过 3 次）：用 `hdc file send` **逐个**推 `/system/lib64` 下的库。
→ 推第一个库的**瞬间**，所有已 mmap 该库的进程立刻 SIGSEGV（`hdcd` 也挂）
→ HDC 断开，**后续文件推不了、重启命令也发不出去** → 只能靠用户断电 → 触发 fscrypt 死锁。

**正确做法**（本次成功验证）：
```bash
# ① 把要安装的文件全部推到 /data/local/tmp/fix/（文件传输阶段不触发 SIGSEGV）
hdc file send libuv.so /data/local/tmp/fix/
hdc file send libscreenlock_server.z.so /data/local/tmp/fix/
hdc file send libdisplay_composer_vdi_impl_default.z.so /data/local/tmp/fix/
hdc file send lubancat-init.sh /data/local/tmp/fix/
hdc file send install.sh /data/local/tmp/fix/

# ② 用 nohup 让设备端脚本【独立】执行安装 + 重启（HDC 断了也不影响）
hdc shell "nohup /system/bin/sh /data/local/tmp/fix/install.sh > /data/local/tmp/fix/install.log 2>&1 &"

# ③ 脚本内容：mount rw → 备份 → cp 覆盖 → chmod → sync → 校验 md5 → 自动 reboot
```
**要点**：安装与重启必须在**设备端同一个脚本**里完成，不能依赖 HDC 会话存活。
脚本模板见 `work/ace-debug-forensics/device_install_patches.sh`。

## 二十七、2026-10-09（续2）：★问题 3/4 根因证实 —— WMS 浮动窗口上限 `1920×vpr` 裁剪 SystemUI

### 27.1 结论

用户反馈的"**虚拟按键明显错位**"（问题3）与"**右上角时间错位**"（问题4）
**根因同一个，且已 100% 证实**：

> **WMS 把 SystemUI 的窗口宽度从 2560 裁到了 1920px，而 launcher 仍是 2560px。**

**并且这是 DPI 修复【引入】的回归** —— DPR=1.5 时上限是 2880px（大于屏宽，不生效）；
DPR=1.0 时上限降到 1920px（小于屏宽，裁剪生效）。

### 27.2 根因代码

`foundation/window/window_manager/wm/src/window_scene_session_impl.cpp:1505`：
```cpp
std::pair<WindowLimits, WindowLimits> WindowSceneSessionImpl::GetSystemSizeLimits(
    uint32_t displayWidth, uint32_t displayHeight, float vpr)
{
    WindowLimits systemLimits;                                       // Physical pixels
    const uint32_t configMaxSize = windowSystemConfig_.maxFloatingWindowSize_;
    systemLimits.maxWidth_  = static_cast<uint32_t>(configMaxSize * vpr);   // ★ 1920 * vpr
    systemLimits.maxHeight_ = static_cast<uint32_t>(configMaxSize * vpr);
```

`maxFloatingWindowSize_` 默认 **1920**：
- `foundation/window/window_manager/wmserver/src/window_layout_policy.cpp:464`（同上算式）
- `foundation/window/window_manager/window_scene/common/include/window_session_property.h:911`
  → `uint32_t maxFloatingWindowSize_ = 1920;  // 1920: default max window size`
- **本板未被覆盖**：`/system/etc/window/resources/window_manager_config.xml` 内**没有** `maxFloatingWindowSize` 节点
  （`vendor/embedfire/lubancat4/window_config/window_manager_config.xml` 同样没有）→ 走默认 1920。

### 28.2 ★ 问题 5 根因查穿：息屏时主动退订公共事件 → 时钟冻结

**结论：不是"界面没重绘"，而是 screenlock 在息屏时【主动退订】了 TIME_TICK 订阅，
导致锁屏时钟在息屏期间完全收不到刷新事件；移动鼠标点亮屏幕 → 重新订阅 → 立刻刷新。**

**根因代码**（`CommonEventManager.ts:92-96`）：
```typescript
function ScreenPolicy(manager: InnerManager): ClearPolicy {
  return sEventManager.subscribe(SCREEN_CHANGE_EVENT, (isScreenOn: boolean) => {
    isScreenOn ? manager.subscriberCommonEvent() : manager.unSubscriberCommonEvent();  // ★息屏退订
  });
}
```
`TimeManager.init()` 里 `this.mManager.applyPolicy([POLICY.SCREEN_POLICY])`（`TimeManager.ts:73`）
把这个策略套到了时钟订阅上 ⇒ **息屏 = 退订 TIME_TICK**。
而 `SCREEN_CHANGE_EVENT` 由 `ScreenLockManager` 订阅 `COMMON_EVENT_SCREEN_OFF/ON` 后发布。

**★设备日志时间线（决定性证据）**：
```
22:46:29.912  screenChangeEvent = true    (亮屏) → 重新订阅
22:46:29.924  CommonEvent_TimeManagerSc --> registerSubscriber success, size: 1
22:47:00      ✓ Time_Change_Event 刷新（正常）
22:47:00.001  screenChangeEvent = false   (息屏!)  → ★退订
22:48:00 ~ 22:59:00   每分钟 TIME_TICK 都在发布（C01202/Unordered 有 12 条）
                      但 ScreenLock 【一条 handle common event 都没有】 → 时钟冻结 13 分钟
23:00:44.513  debounce invoke notifyScreenEvent（鼠标唤醒）
23:00:45.015  screenChangeEvent = true    (亮屏) → 重新订阅
23:00:45.025  registerSubscriber success, size: 1
23:01:00.008  ✓ handle common event: usual.event.TIME_TICK → 立刻刷新到 23:01
```
**完全吻合用户描述**："当前时间是51分，但是显示50，只有移动鼠标才会刷新"。

**电源侧佐证**（`hidumper -s PowerManagerService`）：
```
Current State: SLEEP  Reason: 1     ScreenOffTime: Timeout=30000ms
State: AWAKE   Reason: MOUSE        ← 唤醒源就是鼠标
```
默认 **30 秒**无操作即息屏，所以"看一眼锁屏时钟"时多半已处于退订状态。

**为何是缺陷**：锁屏界面本身的用途就是"看时间"，却在息屏（=正在显示锁屏）期间
退订时间事件。该策略的合理意图应是"**省电**"（屏幕不亮则不刷新），
但 ScreenLock 在这块板上是**屏幕虽 SLEEP、锁屏内容仍在 HDMI 上可见**的场景，
于是暴露出"看得见但不刷新"的矛盾。

### 28.3 问题 5 的候选修法（待选）

| 方案 | 做法 | 评价 |
|---|---|---|
| **① 时钟豁免该策略** | 取消 `TimeManager` 上 `applyPolicy([SCREEN_POLICY])`，让 TIME_TICK 常驻订阅 | 最直接；代价是息屏时也每分钟唤醒一次（省电影响极小，1/min）|
| **② 息屏改本地定时器** | 退订公共事件的同时，用 `setInterval` 每分钟本地刷新（或仅在锁屏可见时）| 更省电，但要处理与 TIME_TICK 的竞争 |
| **③ 依赖输入事件兜底** | 保持现状，靠鼠标/触摸唤醒刷新 | ❌ 不改，用户已明确不接受 |
