## 二、串口交互（一次性命令模式）

> ⚠️ `screen` 在此环境不可用（/run/screen 权限 + 输入传不进）。用 python 直接读写端口。

```bash
stty -F /dev/ttyUSB0 1500000 raw -echo
python3 - <<'EOF'
import os, time, select
fd = os.open('/dev/ttyUSB0', os.O_RDWR | os.O_NOCTTY)
def cmd(c, wait=2):
    while select.select([fd], [], [], 0.05)[0]:
        try: os.read(fd, 4096)
        except Exception: break
    os.write(fd, c.encode()+b'\n')
    time.sleep(wait)
    out = b''
    while select.select([fd], [], [], 0.3)[0]:
        try:
            d = os.read(fd, 4096)
            if not d: break
            out += d
        except Exception: break
    return out.decode(errors='replace')
print(cmd("id"))
os.close(fd)
EOF
```

持续监听（存档）：
```bash
cat /dev/ttyUSB0 | tee /tmp/lubancat4-serial.log
```

串口设备权限问题：`sudo chmod 666 /dev/ttyUSB0`（udev 没给 dialout 组）。

## 三、hdc 连接（TCP）

```bash
HDC=$OH_SRC/prebuilts/ohos-sdk/linux/15/toolchains/hdc
$HDC start                       # 显式启动 server（否则每次调用 server 重启、连接丢失）
$HDC tconn 192.168.x.100:36199 # 注意：此版本无 "connect" 子命令！
$HDC -t 192.168.x.100:36199 shell <cmd>
$HDC list targets -v             # 查看目标
```

**常见坑**：
- 语法是 `hdc tconn ip:port`（不是 `tconn connect ...`）
- 每次 hdc 调用都会查 server，server 不常驻时连接会丢 → 先 `hdc start`
- 板子端口由 `persist.hdc.port` 决定（本板 36199，非默认 8710）

### 板侧 hdcd 手动启动（重启后需重做）
```bash
# 通过串口 shell：
param set const.security.developermode.state true   # hdcd 硬性检查，缺了 exit 255
param set persist.hdc.mode.tcp enable
hdcd -t &                                          # 或由 init 参数任务自动拉起
```

### 网络配置（重启后需重做）
```bash
ifconfig eth0 up
ifconfig eth0 192.168.x.100 netmask 255.255.255.0
```

## 四、修改 ext4 镜像（debugfs 工作流）

> ⚠️ debugfs 两个坑：不能覆盖已有文件（先 rm 再 write）；路径带 / 会变成字面文件名（先 cd 再写）。

```bash
IMG=<FLASH_DIR>/system_mini.img

# 查看
debugfs -R "ls -l /etc/init" $IMG
debugfs -R "cat /etc/init/console.cfg" $IMG

# 写入文件（先删后写，cd 进目录）
printf 'cd /etc/init\nrm console.cfg\nwrite /tmp/console.cfg.new console.cfg\n' > /tmp/dbgfs.cmds
debugfs -w -f /tmp/dbgfs.cmds $IMG

# 目录属性（mode 要十进制！040750 八进制 = 16872 十进制）
debugfs -w -R "mkdir /storage" $IMG
debugfs -w -R "set_inode_field /storage mode 16872" $IMG
debugfs -w -R "set_inode_field /storage uid 1000" $IMG
debugfs -w -R "set_inode_field /storage gid 1000" $IMG

# 完整性校验（必做）
e2fsck -f -y $IMG
```

## 七、softbus_server SIGABRT 排查记录（✅ 已解决 2026-08-17）

**现象**：softbus_server 注册 samgr（SA:4700 OpenSo）成功，~180ms 后 SIGABRT；
deviceauth 等持续 `binder: ... transaction failed 29189/0, target dead`；init 拉黑重启。

**根因（已定位）**：崩溃转储显示 `CFI check failed`，栈在
`InitLaneListener → InitLane → LnnInitLaneHub → BusCenterServerInit → InitSoftBusServer`。
`softbus_server` 库（`dsoftbus/core/frame/BUILD.gn`）无条件开启 `sanitize = {cfi, cfi_cross_dso}`，
但 wifi_direct 等模块仅在 wifi 功能开启时才带 CFI——最小配置无 wifi 部件
（`softbus_communication_wifi_feature=false`）→ 桩模块无 CFI → 调用时 CFI 校验失败 → abort。

**修复**：从 `dsoftbus/core/frame/BUILD.gn` 移除 softbus_server 的 `sanitize` CFI 块，
`hb build -p lubancat4 -T foundation/communication/dsoftbus/core:softbus_server` 重编，
新 `libsoftbus_server.z.so` 无 `__cfi_check/__cfi_slowpath`，注入 system_mini.img 重刷。

**验证**：重启后 `softbus_server` 稳定运行（SA:4700 init 75ms），faultlog 无新 cppcrash。

> 排查要点备忘：softbus 错误走 hilog（hilogd 连接异常），但 **faultloggerd 的
> `/data/log/faultlog/temp/cppcrash-*` 有完整栈**——先看崩溃转储再猜原因。
> `hb build -T` 的目标名不带 `//` 前缀（`foundation/communication/dsoftbus/core:softbus_server`）。

## 十、USB gadget 枚举修复记录（✅ 2026-08-23，根因级）

### 现象

- Windows 能看到 `USB\VID_2207&PID_0018`，但设备永远是 **Unknown Device / CM_PROB_FAILED_START (code 10)**，
  `hdc.exe list targets` 为空；
- 换 WinUSB / libusbK / usbipd / 官方驱动都无效；换 ACM 串口功能也一样失败；
- 板侧特征：每轮枚举恰好 5 个控制请求全部完成（composite_setup 均有响应），然后主机复位重试，
  **永远不出现 `USB_STATE=CONFIGURED`**；Windows 从未发出 SET_CONFIGURATION。

### 排查过程（方法可复用）

1. **内核侧 ftrace 定位**：`composite_setup` 每轮 5 次、`ffs_func_set_alt` 从未被调用
   → 主机卡在"配置前"阶段（描述符/字符串读取），根本没发 SET_CONFIGURATION。
2. **回环测试排除板子**：USB-A→USB-C 线把板子自己的主机口接到 OTG 口，
   板子 Linux 主机一次枚举成功并 `USB_STATE=CONFIGURED` → gadget 本身没问题，问题在 Windows 侧。
3. **OS 描述符探测**：编译静态 aarch64 工具（ioctl USBDEVFS_CONTROL）从板子主机侧
   发 MSFT100/兼容 ID/扩展属性请求 → 全部有效（WINUSB + DeviceInterfaceGUID 正常）→ 排除。
4. **序列号字符串探测**：`GET_DESCRIPTOR(STRING, 3)` 只返回 2 字节（空字符串）！
   cfg 从未设置 `serialnumber`，而 dayu210 会从 eMMC CID 拷贝 → **根因**。

### 修复

```json
// cfg 里 strings/0x409 目录创建后补一行：
"write /config/usb_gadget/g1/strings/0x409/serialnumber LubanCat4-0001",
```

写入后 Windows 一次枚举成功：`device reset → CONNECTED → CONFIGURED`。
同时 v4 cfg 把 UDC 绑定移到 `param:sys.usb.ffs.ready=1` 触发 job（避免开机 ffs 未就绪即绑定的 -19）。

### 持久化

- 本地源码：`device/board/embedfire/lubancat4/cfg/lubancat4-init.cfg`（v4，含 serialnumber）
- 板子现网：`/etc/init/lubancat4-init.cfg` 已覆盖为 v4（remount rw + 备份 `.bak`）
- 教训：**Windows 对"声明了序列号但内容为空"的设备会拒绝枚举，Linux 则容忍**。

## 十二、render_service 起不来根因排查（✅ 2026-08-30，双根因）

### 现象

mini_rich 镜像中 foundation / wms / appfwk 均 ready，SystemUI 进程被 appspawn 拉起，
但 **render_service 反复 exit 255**，HDMI 无桌面画面。

### 根因 A：EGL/GLES 包装库不在 /system/lib64

串口 hilog 关键报错链（pid 4290）：

```
E MUSL-LDSO: Open absolute_path library: check ns accessible failed, pathname /system/lib64/libEGL.so namespace ndk
E C03d00/utils_base: AshmemOpenLocked: fd is invalid, fd = -1, errno = 2
E C02510/display_composer_proxy: InitCmdRequest_: write request failed!
E C01400/Composer: Init: IDisplayComposerInterface::Get return nullptr.
E C01406/OHOS::RS: RSRenderService init failed.
```

原因：OH 的 EGL 包装库（`graphic_2d/frameworks/opengl_wrapper`）内部用**绝对路径** dlopen：

- `libGLESv3.so` → `dlopen("/system/lib64/libEGL.so")`
- `libEGL.so`   → `dlopen("/system/lib64/libGLESv3.so")`

而 mini_rich 打包时这两个库只进了 `/system/lib64/platformsdk/`（SDK 子目录），
`/system/lib64/` 下只有 `libEGL_impl.so` → libmali 的符号链接，没有包装库本体。

修复：从 `out/rk3588/packages/phone/system/lib64/platformsdk/` 拷贝
`libEGL.so`、`libGLESv3.so` 到镜像 `/system/lib64/`（debugfs cd + write，见第四节）。
两者依赖（jsoncpp/appexecfwk_base/ipc_core/want 等在 platformsdk，beget/samgr/surface
等在 chipset-pub-sdk）均可由命名空间默认路径解析，无需再搬。

### 根因 B：内核未开 CONFIG_ASHMEM

`AshmemOpenLocked errno=2` 说明 `/dev/ashmem` 不存在：openharmony-kernel 实际构建用的
`.config` 里 `# CONFIG_ASHMEM is not set`（RK 各 defconfig 默认是 `=y`，被人为关掉）。
OH 的 c_utils ashmem 没有 memfd 回退，display composer 的命令通道必须用它。

修复：`.config` 打开 `CONFIG_ASHMEM=y` → `make olddefconfig` → 重编 Image →
用 HDMI 的 `out/rk-kernel.dtb` + logo 重新打包 → **内核 #14**
（`5.10.209-rk3588 #14 SMP Sun Aug 30 21:25:38 CST 2026`，已验证 vmlinux 含 ashmem_init 符号）。

### 新产物（WSL2 `$HOME/openharmony-lubancat/`）

| 文件 | 说明 | md5 |
|---|---|---|
| boot-ashmem.img | 内核 #14（含 ASHMEM）+ HDMI DTB + logo，40.8MB | — |
| system_mini.img | 已注入 libEGL.so / libGLESv3.so 到 /system/lib64 | — |
| system_mini_orig-20260830.img | 注入前的原始镜像备份 | — |

烧录：Boot(loader) 必选；boot ← boot-ashmem.img；system/rootfs ← system_mini.img；
vendor 不变。预期：/dev/ashmem 出现（0666），render_service 能拿到
display_composer_service，进入桌面验证（sceneboard/launcher）。

### 过程备忘（下次排查可省时间）

- `param set ohos.servicectrl.start <svc>` 有效但 **init 处理有数秒~数十秒延迟**，别急着判断失败。
- render_service 配置了 on-restart：`reset foundation / allocator_host / composer_host`。
  它每退一次 255 就重置整条图形链，形成级联竞态；排查时先 `param set ohos.servicectrl.stop render_service` 打断循环。
- usb_host 因缺 drivers_peripheral_usb 组件持续 SIGSEGV 刷爆 hilog（已知无关问题），
  排查时可用 `param set ohos.servicectrl.stop usb_host` 停掉，避免日志被冲掉。
- composer_host 手动拉起方式（init 的 ctl.start 不总生效）：
  `/vendor/bin/hdf_devhost 11 composer_host -8 1 > /data/composer.log 2>&1 &`
  注册成功标志：hilog `servstat: notify service status display_composer_service, 0`。

## 十三、composer VDI 接口不匹配 + 启动竞态修复（✅ 2026-08-30 第二轮）

### 现象（烧入 libEGL+ASHMEM 修复后）

render_service 不再退在加载阶段（libEGL/ashmem 均通过），能拿到 display_composer_service，
但 composer_host 的 `DisplayComposerService` 创建失败：

```
E COMPOSER_SRV: [LoadVdiAdapter:104] pointer is null and return ret
E COMPOSER_SRV: [DisplayComposerService:65] Create DisplayComposerService failed
→ 服务仍注册成功（空壳），render_service InitCmdRequest_ SendRequest 失败 → 仍退 255
```

### 根因 A：vdi 接口版本不匹配（vendor 镜像缺 vdi_default 库）

OH 5.0.2 的 display "vdi 解耦" 改动后，hdi_service（display_composer_service.cpp）
用 **C 函数表 dlsym**（RegHotPlugCallback/GetDisplayCapability/...）加载 VDI；
而 RK3588 的 `device/soc/rockchip/.../display_composer_vdi_impl.cpp` 仍是**旧工厂模式**
（只导出 CreateComposerVdi）。两者不匹配 → dlsym 全空 → LoadVdiAdapter 失败。

官方产品配置都开了 `drivers_peripheral_display_vdi_default = true`，使 hdi_service
优先 dlopen `libdisplay_composer_vdi_impl_default.z.so`（drivers/peripheral/display
composer/vdi_base 的 **DRM 实现**，新风格 C 函数表，且同款 HdiSession 模型）。
我们的 lubancat4/config.json 没配 → 只加载旧工厂库 → 崩。

修复：
1. `vendor/embedfire/lubancat4/config.json` 给 drivers_peripheral_display 加
   `drivers_peripheral_display_vdi_default = true`（+ community = true）；
2. `./build.sh --product-name lubancat4 -T drivers_peripheral_display`（2.5 分钟）：
   产出新 `libdisplay_composer_vdi_impl_default.z.so`（DRM 实现）、
   新 `libdisplay_buffer_vdi_impl_default.z.so`、带新宏的
   `libdisplay_composer_service_1.2.z.so` / `libdisplay_composer_driver_1.0.z.so`；
3. 注入 vendor_mini.img `/lib64/`（allocator/mapper/metadata 侧旧库已是工厂模式，
   与 allocator_service 的 CreateDisplayBufferVdi dlsym 匹配，**无需动**）。

### 根因 B：启动竞态（render_service 比 composer 早 ~0.4s）

## 十七、合成缓冲 Map failed 代码级定位（2026-09-05 静态分析）

> 本节是无人值守期间在源码/镜像层面的结论。要最终确认哪个环节出错，
> 仍需要板子重新连上后按文末"待执行的验证"抓一次日志。

### 1. Mmap 完整调用链（已逐层读完源码）

出错点在 `BufferQueue::AllocBuffer`，实际是分配成功、映射失败：

```
BufferQueue::RequestBufferLocked
  └─ BufferQueue::AllocBuffer(config)          // foundation/graphic/graphic_surface/surface/src/buffer_queue.cpp:1023
      ├─ SurfaceBufferImpl::Alloc(config)       // 走 HDI 分配 → 成功
      └─ SurfaceBufferImpl::Map()               // 失败 → ret=GSERROR_API_FAILED
          └─ displayBuffer->Mmap(*handle_)
              └─ V1_0 DisplayBufferHdiImpl::Mmap
                  ├─ mapper_ = IMapper::Get(true)   // 注意：true = 本进程 LoadHdiImpl，不是 binder
                  └─ MapperService::Mmap → vdi GbmMmap
                      └─ mmap(NULL, handle->size, RW|MAP_SHARED, handle->fd, 0)
```

关键事实：
- `SurfaceBufferImpl::Alloc` 的分配走 **V1_0 IAllocator binder RPC**（allocator_host），
  BufferHandle 的 fd 靠 NativeBuffer::Marshalling/Unmarshalling 的
  WriteFileDescriptor/ReadFileDescriptor 跨进程传递（代码路径正确）。
- `Mmap` 不走 RPC：`IMapper::Get(true)` 在**调用进程内** dlopen
  `libmapper_service_1.0.z.so`（v1_0 由 `graphic_surface/surface/BUILD.gn`
  依赖 `libdisplay_buffer_hdi_impl_v1_2` 带入），再 dlopen VDI
  `libdisplay_buffer_vdi_impl_default.z.so`（因 config 已开
  `drivers_peripheral_display_vdi_default=true`）。
- 因此 virAddr 更新是**就地**的：`GbmMmap(buffer)` 会把 mmap 结果写回
  `buffer->virAddr`，只要 buffer 是调用方进程内的 handle 副本，返回即有效。

### 2. 镜像/库核对（已用 debugfs 检查 2026-09-05 的 system/vendor 镜像）

| 项目 | 结果 |
|---|---|
| `libmapper_service_1.0.z.so` / `1.2` / `libmetadata_service_1.1` | 在 vendor 镜像 `/lib64/chipsetsdk/`（driver 库在 `/lib64`） |
| namespace `ld-musl-namespace-aarch64.ini` | `default.lib.paths` 含 `/vendor/lib64/chipsetsdk`，dlopen 可达 |
| mapper service 的 DT_NEEDED（utils/hdi/hilog/hitrace/ipc/sec_shared/ubsan） | system 与 vendor 镜像均存在 |
| VDI default / vendor 库 | 均在 `/lib64`：`libdisplay_buffer_vdi_impl_default.z.so`(29KB 新) 与 `libdisplay_buffer_vdi_impl.z.so`(9.9KB 旧工厂) |
| `MapperImplGetInstance` / `CreateDisplayBufferVdi` | 均已导出（待实机确认 dlopen 顺序） |

结论：库不缺失、namespace 可达。运行时若仍失败，不是"文件找不到"这一层，
除非 mapper 在 RS/launcher 的**沙箱限制**下 dlopen 行为与 host 不同
（host 已能注册服务并分配成功，这条概率较低）。

### 3. 可能根因（按概率排序，等日志裁决）

1. **`handle->fd` 客户端无效**：RS/launcher 从 allocator RPC 拿到 fd 后，
   在调用 Mmap 前 fd 已被某处关闭（或回复 parcel 的 fd 传递竞态）。
   现场曾观察到"RS 进程 fdinfo 无该 dma-buf"——但该观察是在 Map 失败、
   SurfaceBuffer 析构（会 close fd）之后做的，不能证明 fd 从未到达；
   必须在失败瞬间取证。
2. **MapperService 的 VDI 加载失败**：本地 mapper 实例创建成功但不代表
   `vdiImpl_` 非空；`LoadVdi()` 两段 dlopen 都失败时 Mmap 直接返回失败。
   AllocMem 成功只证明 **allocator_host** 的 VDI OK，不等于 RS 内 mapper VDI OK。
3. **mmap 本身失败**：fd 有效但 `size` 为 0 / 超过 dma-buf 实际大小 /
   fd 指向非 dma-buf。GBM 已有日志（含 errno），抓日志即可区分。
4. **mapper_ 实际是 binder proxy**（远程）：代码上是 `Get(true)` 本地加载，
   但如果实际链接到的 IDisplayBuffer 实现库与源码不一致，Mmap 的 virAddr
   不会写回本地 handle → 必然 null。

### 4. 待执行的验证（板子重新上电 / USB 透传恢复后）

- 若 1（fd 无效）：先查 allocator stub reply 与 client ReadStrongParcelable
  之间的 fd 所有权，必要时把 `DisplayBufferHdiImpl` 的 Alloc 也改为

- 若 2（VDI 未加载）：核对 RS 沙箱内 `dlopen("libdisplay_buffer_vdi_impl_default.z.so")`
  是否被 allowed_libs 拦截，或回退 vendor VDI（工厂库）单独给 mapper；
- 若 3（mmap errno）：按 errno 修（EBADF=fd 无效、EINVAL=size/长度问题、
  ENOMEM 等），重点核对 GbmAllocMem 写回的 `size` 与 `hdi_gbm_bo_get_size` 返回值；
- 若 4（远程 mapper）：给 `IDisplayBuffer::Get()`/`IMapper::Get()` 打印
  `IsProxy()` 确认，并把 mapper 也改为本进程直通实现。

```
3375 MAPPER_SRV: MapperService: Load buffer VDI failed
3375 MAPPER_SRV: [Mmap:129] pointer is null and return ret   ← vdiImpl_ 为 NULL
1112 Bufferqueue: AllocBuffer: Map failed, ret:50001000
3182 native_window: RequestBuffer ret:50002000
```

### 根因

- `SurfaceBufferImpl::Map()` 的 Mapper 是 **本进程内 LoadHdiImpl 的
  MapperService**（`IMapper::Get(true)`），它需要 dlopen buffer VDI：
  `libdisplay_buffer_vdi_impl.z.so`（当前镜像该 service 未启用
  BUFFER_VDI_DEFAULT_LIBRARY_ENABLE，只会回退/直接加载这个 vendor 库）。
- 该 vendor VDI 库（及其依赖 `libdisplay_buffer_vendor.z.so`）只存在于
  **/vendor/lib64**；而 render_service 运行在 system 沙箱，其 ld-musl
  **default namespace 只含 /system/lib64，不含 /vendor/lib64** →
  RS 进程内 dlopen 失败 → vdiImpl_ = nullptr → Mmap 恒失败。
- allocator_host/composer_host 等 **vendor host 进程没有此限制**，
  所以 AllocMem 正常、只有 Map 失败。此前"fd 没到 RS"的猜测不成立。

### 修复（热验证通过）

把两个 VDI 库复制进 `/system/lib64`（RS default namespace 可达）：

```sh
mount -o remount,rw /
cp /vendor/lib64/libdisplay_buffer_vdi_impl.z.so  /system/lib64/
cp /vendor/lib64/libdisplay_buffer_vendor.z.so   /system/lib64/
```

重启 render_service + launcher 后日志确认：
- `RSScreenManager Init succeed`、`HgmCore adding screen : 0`；
- 不再出现 MAPPER_SRV LoadVdi/Mmap 失败、不再有 Map failed；
- launcher 正常执行 `LauncherMainAbility onRequest` / `EntryView voteBootEvent`；
- DoComposition 持续刷新。

## 二十一、VSync 缺失根因与 vdi_base RegRefreshCallback 实现（✅ 修复验证中）

### 干净启动确认

- 刷 system_mini_ui-fix.img 后干净 boot：render_service/launcher ready；
- 手动重启 RS 后屏幕注册成功（阻塞 A 时序竞态仍存在于冷启动，需后续固化）；
- launcher 窗口 foreground、首帧 vsync 收到，但 **FlushImplicitTransaction
  empty + RS transaction curIndex 恒 0**，ArkUI 无绘制事务；
- 关键新证据：
  ```
  464 display_composer_stub: RegRefreshCallback_ failed, error code is -2
  1781 display_composer_proxy: RegRefreshCallback_ failed, error code is -2
  1781 Composer: RegScreenRefresh: RegRefreshCallback failed, ret is -5
  RSScreenManager Init: Failed to register OnRefresh Func to composer
  ```
  VSyncGenerator 只发出一次 First vsync，此后**无持续 vsync** → UI 无后续帧驱动。

### 根因

vdi_base DRM 后端的 `RegRefreshCallback` 是 **stub**（恒
`HDF_ERR_NOT_SUPPORT`）。OHOS 5.0 的 RS 依赖该全局刷新回调获取持续 vsync，
stub 导致 vsync 只发一次、ArkUI 停摆。

### 修复（源码）

`display_composer_vdi_impl.cpp`：
- 新增 trampoline（VBlank 回调转发 RefreshCallback，devId=0）；
- `RegRefreshCallback` 不再 stub：保存 cb/data 并把 trampoline 注册到
  `DrmVsyncWorker`，由 DRM vblank worker 驱动持续刷新。

已重编 drivers_peripheral_display（1:51 成功），新库
`libdisplay_composer_vdi_impl_default.z.so` 导出 RegRefreshCallback（296B 实现）。

|---|---|

## 二十五、桌面恢复修复实录（2026-09-05 下午，串口逐步验证）

### 关键认识：两套 user 体系并存
- 本固件主用户为 **user100**（launcher uid=20010013，base 20010000+idx）；
  但 bmsdb 残留里部分 bundle 记录在 **user0**（uid 10004=contacts 等，
  数据在 `/data/app/el1/0/`，12:53 时代遗留）→ 一个系统两个 uid 世界。
- bmsdb 被清空后 BMS 预置安装会落到 **user0**（`/data/app/el1/0/`），
  而 launcher/桌面要 **user100** → 表现为"无桌面"。
- installs(SA:511) 每 boot 只在 74s→211s 窗口内安装，**一次装不完
  /system/app 全部**（每次只处理一部分，且依赖 bmsdb 已有记录），
  目录不存在/缺记录时不会自动补 → 需手动重建。

### 已恢复"桌面可用"状态
关键动作：**为 user100 重建 `/data/app/el1/100/{base,database}` 及每个
已注册 bundle 的子目录**（纯 `mkdir`，无需 chown 即可让 appspawn bind 通过）：
```
mkdir -p /data/app/el1/100/base /data/app/el1/100/database   # 顶层
# 顶层属主：base=0:2000 drwxr-xr-x; database=3060:3060 drwxr-xr-x
# 每个 bundle：
mkdir -p /data/app/el1/100/base/<bundle> /data/app/el1/100/database/<bundle>
# 子目录最终属主应为 uid:uid (base) / uid:3012 (database)、0700/2770
```
效果：目录补好后 AMS 自动重启 launcher，**bootevent.launcher.ready +
wms.fullscreen.ready 置位，桌面恢复**（pid 14664 稳定）。
→ 应用 spawn 失败(`0xd000009`)根因 = **user100 数据目录缺失**，实锤。
