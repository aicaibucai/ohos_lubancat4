# 第一部分：移植风险清单

## 风险全景（按严重度）

```
高  ├─ 内核版本与闭源固件不匹配 (R1)  ← 一票否决型
    ├─ RK3588S vs RK3588 DTS 差异 (R2)
    ├─ RK loader/DDR 配置 (R3)
    └─ 分区方案不匹配 (R4)
中  ├─ GPU/显示点亮 (R5)  WiFi 型号 (R6)  SELinux 策略 (R7)  编译环境 (R8)
低  └─ hdf 配置 (R9)  触摸/音频 codec (R10)
```

## 一、内核相关（最高优先级）

### R1. 内核版本与闭源二进制固件不匹配 ⭐⭐⭐⭐⭐【致命】
- 现象：GPU 报 firmware load failed、视频硬解 crash、ISP 段错误、花屏。
- 根因：Mali/VPU/NPU/ISP 固件与内核驱动 ABI 强绑定。
- 规避：首版死守 linux-5.10，固件直接复用；换内核 = 整套固件+驱动一起搬。

### R2. RK3588S 与 RK3588 DTS 差异 ⭐⭐⭐⭐☆
- 现象：套 dayu210 DTS 后大量外设 failed to probe（显示/PCIe/USB/GMAC）。
- 解决：以 LubanCat SDK 的 `rk3588s-lubancat-4.dts` 为事实依据；先禁用非必要外设保证启动。

### R3. RK loader / DDR 初始化配置 ⭐⭐⭐⭐☆
- 现象：烧录后完全无反应；DDR 训练失败、内存容量识别错误。
- 解决：优先用 LubanCat SDK 的 RK3588S 专用 loader（`MiniLoaderAll_lubancat.bin`）。

## 二、引导与分区

### R4. OH 分区与 RK parameter.txt 不匹配 ⭐⭐⭐⭐☆
- 现象：无法 mount rootfs、挂错分区、userdata 丢失。
- 解决：以 dayu210 parameter.txt 为模板，按 eMMC 容量缩放；确认 root=PARTUUID 指向。

### R5. U-Boot 与 OH 镜像格式对接 ⭐⭐☆☆☆
- 现象：U-Boot 找不到 kernel、boot_linux 解包失败。
- 解决：OH uboot 的 bootrkp 能读 RK 格式 boot.img（本板已验证）；避免 ext2 boot_linux 格式混用。

## 三、构建系统

### R6. 编译环境依赖缺失 ⭐⭐☆☆☆【高频但易解】
- 现象：python 模块缺失、gn/ninja 版本错、llvm 下载超时。
- 解决：严格按官方装依赖；pip 换国内源；先编 dayu210 隔离环境问题。

### R7. 产品未注册 ⭐⭐☆☆☆
- `--product-name lubancat4` not found → 在 productdefine 或 config.json inherit 链注册。

### R8. BUILD.gn 硬编码路径 ⭐⭐★☆☆
- 全局搜索 `dayu210`/`hihope` 替换；**`//device/soc/rockchip/rk3588` 公共路径不要改**。

## 四、HAL / 外设

### R9. GPU（Mali-G610）点不亮 ⭐⭐⭐★☆
- 固件放 /vendor/firmware；首版关 Mesa3D 用 RK 闭源栈；对照 LubanCat DTS 的 GPU 节点。

### R10. 显示输出不匹配 ⭐⭐★☆☆
- 以 SDK DTS 的 `&hdmi`/`&mipi_dsi0` 状态为准。

### R11. WiFi 型号不一致 ⭐★★☆☆
- dayu210 带 ap6xxx；LubanCat4 实际型号需确认（本板日志显示 rtl8188ee，待 P4 处理）。

### R12. 触摸屏 / 音频 codec 不匹配 ⭐★★☆☆
- 从 LubanCat DTS 找 IC 型号，改 DTS 节点即可（内核通常已带驱动）。

## 五、系统与安全

### R13. SELinux 策略缺失 ⭐⭐★☆☆
- 首版保持 `build_selinux: false`，跑通后再补。

### R14. OH 安全模块（tzdriver/xpm/code_sign）与内核冲突 ⭐⭐★☆☆
- 首版跳过非必需安全补丁；调通后逐个启用。

## 六、调试与工具

### R15. hdc 连不上 ⭐★★☆☆
- 先靠串口；USB 起来后 hdc 用法同 adb。**本板已打通 hdc TCP**（见 04 文档）。

### R16. 串口调试信息不足 ⭐★★☆☆
- cmdline 加 `loglevel=8 earlycon`；用 hilog。

### R17. 编译时间长 ⭐★★☆☆【影响体验】
- 必用 `--ccache`；只编内核用 build_kernel.sh 或直接 make。

## 七、针对"Android + 弱 C/C++"的特有风险

- **R18** 别以为能像 Android 那样 adb push 热替换：OH 分区只读+verity，调试期可改可写模式。
- **R19** 改 C 引入语法错误看不懂报错 → 让 AI 读报错改代码（见下文工具链）。
- **R20** GN/Ninja 与 Soong/Gradle 心智不同 → 改 BUILD.gn/.gni 必须重新 gn gen。

## 八、风险应对总策略

1. 小步快跑、隔离变量；2. 先求能跑再求跑好；3. 永远有串口；4. 保留可回滚镜像；5. 善用 dayu210 参照；6. C/C++ 交给 AI。

# 第二部分：Android → OpenHarmony 知识迁移

## 一、架构映射表

| 概念 | Android | OpenHarmony | 备注 |
|---|---|---|---|
| 系统型态 | AOSP | **标准系统 standard** | LubanCat4 用 standard |
| 设备树 | device tree | **DTS**（Linux 内核） | 完全一样 |
| 引导 | bootloader→aboot→kernel | BootROM→loader(rkbin)→U-Boot→kernel | RK 私有 loader |
| 编译框架 | Soong (Android.bp) | **GN (BUILD.gn) + Ninja** | 心智接近，语法不同 |
| 构建入口 | `m`/`lunch` | `./build.sh --product-name X` | lunch≈选 product |
| 产品定义 | `device/<oem>/<device>` | `vendor/<oem>/<product>/config.json` + `device/board/...` | 拆两处 |
| HAL | HIDL/AIDL + HAL | **HDF** | 用 .idl 描述接口 |
| adb / logcat | adb / logcat | **hdc** / **hilog** | 命令几乎一样 |
| init | init + .rc | **init** + .cfg/.json | 类似 |
| selinux | sepolicy (.te) | **selinux** (.te) | 语法同源 |
| 分区 | system/vendor/userdata/boot | system/vendor/userdata/boot_linux/ramdisk/sysprod/chipset/updater | 更多 |

## 二、目录结构映射（你主要在哪改）

```
openharmony6-lts/
├── device/soc/rockchip/rk3588/   SoC 支持（公共，少改）
├── device/board/<oem>/<board>/   板级 ★重点改
├── vendor/<oem>/<product>/       产品配置 ★重点改（config.json≈device.mk）
├── kernel/linux/linux-5.10       内核源码
├── drivers/hdf_core/             HDF 框架
├── build/  out/  prebuilts/      构建系统/产物/工具链
```

**关键认知**：大部分改动是配置（BUILD.gn/config.json/DTS/shell），不是写 C。

## 三、GN + Ninja 速成

- GN 读 BUILD.gn 生成 build.ninja；Ninja 执行编译。
- 最小语法：`shared_library("name") { sources=[]; deps=["//path:target"] }`（`//`=绝对路径，`:`=目标名）。
- 改了 BUILD.gn 没生效 → 没重新 gn gen（跑 build.sh 会自动生成）。
- 复制 dayu210 的 BUILD.gn 改名即可，**别碰复杂 GN 逻辑**。

## 四、DTS 速成（你的主战场）

```dts
&uart2 {                          // & 引用 SoC 已定义的控制器
    status = "okay";              // 启用/禁用
    pinctrl-0 = <&uart2m1_xfer>;  // 引脚复用（RK3588S 关键）
};
&i2c0 {
    status = "okay";
    gt9xx@5d {                    // 触摸屏
        compatible = "goodix,gt9886";  // 驱动匹配字符串 ★关键
        reg = <0x5d>;
        interrupt-parent = <&gpio0>;
        interrupts = <3 IRQ_TYPE_EDGE_FALLING>;
        touch-gpio = <&gpio0 3 GPIO_ACTIVE_HIGH>;
    };
};
```

安全套路：**永远从 LubanCat SDK 的 DTS 抄**；对照状态/引脚/参数；RK3588S 一般兼容 `rockchip,rk3588`，个别节点用 `rk3588s`，以 SDK 为准。

## 五、C/C++ 够用清单（不学也行的部分）

- 你只需会读：改字符串常量、注释代码、调 #define/结构体字段。
- 记忆点：`.` 用于结构体本身，`->` 用于指针；`负数=出错，0=成功`；`NULL`≈null；`void*`≈Object。
- 读编译错误：`src/foo.c:42:5: error: ...` = 文件:行:列 + 错误类型，把这段贴给 AI 修。
- 编译输出：`CC`=编译，`LD`=链接，`Error 1/2`=有错，往上找第一个 `error:`。

## 六、HDF 够用版

- HDF = OH 驱动框架（≈Android HAL）。接口 .idl、配置 .hcs、驱动 C/C++。
- 移植阶段基本不写驱动，只用现成 RK 驱动；在 vendor hdf_config 里复制 dayu210 的 .hcs 按板卡调整。
- 把 HDF 当"另一套 HAL"就行。

## 七、工具链（弥补 C 弱点的利器）

| 场景 | 工具 |
|---|---|
| 读不懂/不会写 C | Copilot Chat / Claude（描述意图→给代码+解释） |
| 改编译报错 | 同上（贴完整报错→修复+说明） |
| 看代码结构 | VS Code + clangd |
| 全局搜索 | ripgrep（`rg "dayu210"`） |
| 内核配置 | `make menuconfig` |
| DTS 编辑 | VS Code + DeviceTree 插件 |

## 八、调试流程（套用 Android 经验）

`问题→复现→缩小范围→定位→修复→验证`。招数：日志优先（hilog/dmesg）、二分回退、对比参照板（dayu210）、最小系统法。

## 九、常用命令

```bash
./build.sh --product-name lubancat4 --ccache          # 编译
hdc list targets / hdc shell / hdc file send          # ≈ adb
hdc -t <key> shell dmesg | tail -50                   # 内核日志
hdc -t <key> shell param get const.ohos.fullname.release  # OH 版本
```

## 十、学习优先级

★★★★★ DTS + RK pinctrl ｜ ★★★★★ GN 基本语法 ｜ ★★★★☆ hdc/hilog/menuconfig ｜ ★★★☆☆ 读 C 基础 ｜ ★★☆☆☆ HDF 概念 ｜ ❌ 系统学 C++（移植不需要）

## 十一、心态

1. 你是工程师不是 C 程序员；2. 配置>代码；3. 对照>创造（先看 dayu210 怎么做）；4. 工具是杠杆；5. 小步快跑；6. 保留黄金镜像。
